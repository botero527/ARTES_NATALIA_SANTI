02 · FundamentosFunciones — Bloques Reutilizables

Una función es un bloque de código con nombre que puedes llamar cuantas veces quieras. Parámetros son lo que le mandas; return es lo que te devuelve.

pythondef saludar(nombre):
    return f"Hola, {nombre}!"

saludar("Natalia")  # → "Hola, Natalia!"
saludar("Luis")     # → "Hola, Luis!"  ← misma función, diferente dato

Parámetros con valor por defecto

Si no mandas ese parámetro, usa el valor que pusiste por defecto:

pythondef conectar(host, puerto=1433, timeout=30):
    return f"Conectando a {host}:{puerto}..."

conectar("azure.sql.com")            # usa puerto=1433, timeout=30
conectar("azure.sql.com", puerto=5432)  # cambia solo el puerto
En tu proyecto: _limpiar_nombre(s), _ruta_arte_salida(), _anular_bd() — todas son funciones así. Las defines una vez, las llamas desde donde las necesites.

Lambda — función en una línea

Para funciones cortitas que solo usas una vez, Python tiene lambda:

python# En vez de definir una función aparte:
def doble(x): return x * 2

# Lambda hace lo mismo en una línea:

# En tu proyecto lo viste así — pasando funciones a botones:

Regla de oro: Si el mismo bloque de código aparece 2 veces en tu código, conviértelo en función. Si aparece 3 veces y no es función, hay un problema.

04 · IntermedioClases y Programación Orientada a Objetos (POO)

Una clase es un molde para crear objetos. Un objeto tiene atributos (datos que guarda) y métodos (cosas que puede hacer).

Piénsalo así: Clase = plano de un carro. Objeto = el carro físico que fabricas con ese plano.

pythonclass AutoCADMotor:
    # __init__ se llama automático cuando creas el objeto
    # "self" es el objeto mismo — siempre es el primer parámetro
    def __init__(self):
        self.acad = win32com.GetActiveObject("AutoCAD.Application")

    def abrir(self, ruta):
        doc = self.acad.Documents.Open(ruta)
        return doc

    def quit(self):
        self.acad = None

# Usar la clase:
motor = AutoCADMotor()   # → llama __init__, crea el objeto
doc   = motor.abrir("C:/planos/pieza.dwg")
motor.quit()

05 · IntermedioExcepciones — Manejar Errores sin Caerse

Cuando algo falla en Python, lanza una excepción. Si no la atrapas, el programa se muere. Con try/except la atrapas y decides qué hacer.

pythontry:
    resultado = 10 / 0             # ← esto falla
except ZeroDivisionError as e:
    print(f"Error: {e}")           # → "Error: division by zero"
finally:
    print("Esto siempre se ejecuta")  # con o sin error

Crear tus propias excepciones

Puedes crear excepciones personalizadas para situaciones específicas de TU lógica:

python# Esto lo hicimos juntos en crear_arte_acad.py

    """El arte se creó OK pero falló al guardar en disco."""
    pass

# Luego la lanzamos en SaveAs:
try:
    doc.SaveAs(ruta)

    raise ErrorGuardadoArte(f"No se pudo guardar: {e}")

# Y en agp_app.py la atrapamos separada para NO cancelar el código BD:
except ErrorGuardadoArte as e:

except Exception as e:

    _anular_bd(valores)  # esto sí cancela porque fue un error real
Regla práctica: Siempre atrapa la excepción más específica primero. Python revisa los except de arriba a abajo y se queda con el primero que coincida.

07 · En tu ProyectoThreads — Hacer Varias Cosas a la Vez

Python normalmente corre código línea por línea — una cosa a la vez. El problema: si tienes una operación lenta (conectar a BD, procesar un DWG en AutoCAD), la interfaz gráfica se congela y parece que crasheó.

Los threads (hilos) te permiten correr esa operación lenta en un hilo separado mientras la interfaz sigue respondiendo.

pythonimport threading

# SIN thread — la UI se congela mientras procesa:
def _crear_arte(self):
    time.sleep(10)         # ← la ventana muere 10 segundos
    log("Listo")

# CON thread — la UI sigue viva:
def _crear_arte(self):
    self._busy(True)        # ← muestra spinner
    threading.Thread(
        target=self._t_crear,  # ← función que corre en el hilo
        daemon=True           # ← muere si se cierra la app
    ).start()

def _t_crear(self):          # este corre en segundo plano
    time.sleep(10)
    self.after(0, lambda: log("Listo"))  # ← vuelve al hilo UI
Regla importante: Nunca toques la interfaz gráfica desde un thread. Siempre usa self.after(0, funcion) para enviarle el mensaje al hilo principal de la UI. Si no, crashea silenciosamente.

El patrón que usamos: _accion() lanza, _t_accion() trabaja

En tu proyecto todos los botones siguen este patrón. El nombre del método con _t_ significa "thread":

MétodoHiloQué hace
_crear_arte()UI (principal)Valida campos, lanza el thread
_t_crear()BackgroundLlama AutoCAD, genera el DWG — puede tardar
_todo_en_uno()UI (principal)Muestra diálogo cajetín, lanza thread
_t_todo()BackgroundExtraer plano + crear arte + guardar BD

08 · En tu ProyectoBases de Datos y SQL

Una base de datos es como un Excel gigante pero estructurado, rápido y con múltiples usuarios al mismo tiempo. SQL es el lenguaje para hablar con ella.

Las 4 operaciones básicas (CRUD)

sql-- CREATE → insertar un registro nuevo
INSERT INTO mallas.vitrojet (vitro, codigo_malla, vehiculo)
VALUES ('V-0042', 'M-0010', 'CHEVROLET TAHOE');

-- READ → consultar / buscar
SELECT vitro, vehiculo, ruta
FROM mallas.vitrojet
WHERE vehiculo LIKE '%TAHOE%'
ORDER BY vitro DESC;

-- UPDATE → modificar algo que ya existe
UPDATE mallas.vitrojet
SET    ruta = '\\server\artes\V-0042.dwg',
       modificado_por = 'abotero'
WHERE  vitro = 'V-0042';

-- DELETE → borrar (úsalo con cuidado)
DELETE FROM mallas.vitrojet
WHERE vitro = 'V-0042';

Cómo Python habla con la BD (pymssql)

pythonimport pymssql

conn = pymssql.connect(server="tu.database.windows.net",
                       user="admin", password="***",
                       database="AGP_BD")
cur = conn.cursor()

# %s es el placeholder — NUNCA armes la query con f-string + datos
# porque abre la puerta a SQL Injection (te explico abajo)
cur.execute(
    "SELECT nombre FROM MALLAS.APP_USUARIOS WHERE usuario=%s",
    ("abotero",)   # ← tupla con los valores
)
fila = cur.fetchone()   # una fila
filas = cur.fetchall()  # todas las filas

conn.commit()   # confirmar cambios (INSERT/UPDATE/DELETE)
conn.close()
SQL Injection — nunca hagas esto:
f"SELECT * FROM usuarios WHERE usuario='{input_usuario}'"

Si alguien escribe ' OR 1=1 -- como usuario, esa query se convierte en "dame TODOS los usuarios". Siempre usa %s con parámetros separados.

Transacciones — o todo o nada

Una transacción agrupa varias operaciones: si falla cualquiera, se deshacen todas. Como un "ctrl+z" automático de la BD.

pythontry:
    cur.execute("INSERT INTO mallas.vitrojet ...")
    cur.execute("UPDATE mallas.grandes ...")
    conn.commit()    # ← confirma AMBAS operaciones juntas
except Exception:
    conn.rollback()  # ← si algo falla, deshace todo
    raise

09 · En tu ProyectoInterfaces Gráficas con customtkinter

customtkinter (ctk) es una librería para hacer ventanas en Python con diseño moderno. Tu app entera está construida con esto.

El concepto de Widget

Cada elemento visible es un widget: botón, campo de texto, etiqueta, tabla... Los widgets se anidan: el Frame contiene Buttons que contienen Labels.

pythonimport customtkinter as ctk

app = ctk.CTk()                          # ventana raíz

frame = ctk.CTkFrame(app)                # contenedor
frame.pack(fill="both", expand=True)

label = ctk.CTkLabel(frame, text="Hola!")
label.pack(pady=20)

entry = ctk.CTkEntry(frame, placeholder_text="Escribe aquí...")
entry.pack(pady=10)

btn = ctk.CTkButton(frame, text="Enviar",
                    command=lambda: print(entry.get()))
btn.pack(pady=10)

app.mainloop()   # ← inicia el loop de eventos, la ventana se queda abierta

pack vs grid — dos formas de posicionar

pack — apila elementos
label.pack(side="top")
btn.pack(side="bottom")
# Simples, para layouts lineales
grid — cuadrícula exacta
label.grid(row=0, col=0)
btn.grid(row=1, col=1)
# Para layouts precisos, tipo formulario
Nunca mezcles pack y grid en el mismo contenedor. Python te da error. En tu proyecto usamos grid para las pestañas principales y pack para elementos simples dentro de frames.

10 · En tu ProyectoEventos y Callbacks — La UI Reacciona

Un evento es algo que pasa: el usuario hace clic, escribe una tecla, mueve el mouse. Un callback es la función que se llama cuando ese evento ocurre.

python# Callback de botón — se llama al hacer clic
btn = ctk.CTkButton(text="Crear Arte", command=self._crear_arte)

# Bind — conecta cualquier evento a cualquier función
entry.bind("<Return>",     self._on_enter)   # ← tecla Enter
entry.bind("<KeyRelease>",  self._on_key)     # ← cada tecla suelta
entry.bind("<FocusOut>",    self._on_blur)    # ← sale del campo
tree.bind("<Double-1>",     self._on_doble)   # ← doble clic
tree.bind("<MouseWheel>",   self._on_scroll)  # ← rueda del mouse

El patrón de búsqueda con debounce

En tu TabBD cuando escribes en el buscador no hace una query a la BD por cada letra — espera 300ms a que pares de escribir. Eso se llama debounce:

pythondef _on_key(self, _):
    # Si ya había un timer corriendo, cancelarlo
    if self._timer:
        self.after_cancel(self._timer)

    # Crear uno nuevo que dispara en 300ms
    self._timer = self.after(300, self._do_search)

# Resultado: solo hace la búsqueda cuando el usuario
# para de escribir por 0.3 segundos

11 · Conceptos ClaveLibrería vs Framework vs API

Estos tres términos se confunden mucho. La diferencia real:

TérminoQué esQuién controla el flujoEjemplo en tu proyecto
Librería Colección de funciones/clases que TÚ llamas cuando quieres Tú pymssql, ezdxf, openpyxl
Framework Esqueleto que define cómo se estructura tu app. Él te llama a ti. El framework customtkinter (mainloop llama tus callbacks)
API Interfaz para hablar con otro sistema o programa Nadie — es el contrato entre dos sistemas Azure SQL, SAP, SmartFactory, AutoCAD COM

12 · Conceptos ClaveGit — Control de Versiones

Git es como un historial de guardados con nombres. Nunca más vas a perder código por accidente, y puedes trabajar con otros sin pisarse.

bash# Los comandos que usas el 90% del tiempo:

git status                  # ¿qué cambié?
git diff                    # ver exactamente qué líneas cambiaron

git add archivo.py          # marcar archivo para guardar
git add .                   # marcar TODOS los cambios

git commit -m "arreglo bug del SaveAs"  # guardar con mensaje

git log --oneline           # ver historial de commits
git diff HEAD~1             # qué cambió desde el commit anterior

git checkout -- archivo.py  # deshacer cambios en un archivo
git stash                   # guardar cambios temporalmente

El flujo de trabajo

bash# 1. Crear una rama para el cambio nuevo (no tocar main)
git checkout -b fix/error-guardado-arte

# 2. Hacer tus cambios, probar
# 3. Guardar
git add .
git commit -m "no cancelar BD cuando falla SaveAs"

# 4. Volver a main y unir tu rama
git checkout main
git merge fix/error-guardado-arte
Regla de commits: Commits pequeños y frecuentes > un commit gigante con todo. El mensaje debe decir QUÉ y POR QUÉ, no cómo (el cómo ya está en el código).

13 · MentalidadCómo Pensar Como Dev

Divide y vencerás

Cuando tienes un problema grande, nunca lo atacas todo de un golpe. Lo partes en pedazos hasta que cada pedazo sea simple:

textoTarea: "Crear arte automáticamente"

↓ Divide:
├── Abrir AutoCAD y el DWG
├── Extraer solo los layers que necesito
├── Llenar el cajetín con los datos
├── Guardar el archivo con el nombre correcto
└── Registrar el vitro/malla en la BD

↓ Divide más "Guardar con nombre correcto":
├── Leer malla y pieza del formulario
├── Limpiar caracteres inválidos (/ \ : etc)
├── Construir la ruta completa
└── Llamar doc.SaveAs(ruta)

Leer errores — el superpoder más importante

El 80% de aprender a programar es aprender a leer los mensajes de error. No son enemigos — te están diciendo exactamente qué salió mal:

tracebackTraceback (most recent call last):
  File "agp_app.py", line 789, in _t_todo
    _anular_bd(valores, self._log_fn)          ← línea donde explotó
  File "agp_app.py", line 415, in _anular_bd

                           código de error       mensaje legible

Lee de abajo hacia arriba. La última línea es el error real. Las de arriba son el camino que siguió el código hasta llegar ahí.

El ciclo del dev

texto1. Entender qué debe hacer (antes de escribir UNA línea)
2. Escribir el código más simple posible que funcione
3. Probarlo — encontrar qué falla
4. Arreglarlo
5. Volver al 3 hasta que funcione
6. Limpiar el código (refactoring)
7. Documentar si algo es no obvio

Señales de que vas por buen camino

✓ Si borras tu código y lo reescribes en la mitad de líneas — vas mejorando.
✓ Si lees código de hace 3 meses y lo entiendes — vas mejorando.
✓ Si cuando algo falla ya sabes en qué zona buscar — vas mejorando.
✓ Si puedes explicarle tu código a alguien más — lo entiendes de verdad.

El secreto que nadie dice: Los buenos devs no memorizan todo. Saben cómo buscar, cómo leer documentación, y cómo hacer las preguntas correctas. Google y la documentación oficial son herramientas de trabajo, no trampa.
